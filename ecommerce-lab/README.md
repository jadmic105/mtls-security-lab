# E-commerce mTLS Lab

A small e-commerce checkout built the way a payment flow should be secured: public TLS for customers, mTLS with caller authorization between internal services, a separate trust domain for the payment provider, signed webhooks, and no raw card data on our servers. Every control is checked by an automated test that also proves it **fails closed**.

## Architecture

```
Customer (browser/curl)
   │  ① HTTPS, no client cert
   ▼
nginx edge :8443 ──────────────── /webhooks/ ─────────────┐
   │  ② mTLS as "edge"                                      │ ② mTLS as "edge"
   ▼                                                        ▼
orders sidecar :9101  (allows: edge)          payments sidecar :9102
   │                                           (allows: orders → /charge, edge → /webhooks/)
   ▼                                                        ▲   │
Orders app :8001 ──── ③ mTLS as "orders" ───────────────────┘   ▼
                                                     Payments app :8002
                                                            │  ④ mTLS as "merchant-payments"
                                                            │     (PSP CA) + API key
                                                            ▼
                                                 Mock PSP gateway :9103 → app :8003
```

| Component | Role |
|---|---|
| **nginx edge** | Terminates customer TLS, adds HSTS, routes `/api/` to orders and `/webhooks/` to payments, presenting the `edge` client certificate |
| **nginx sidecars** | One per service, like a service-mesh proxy. Verify the caller's certificate, enforce an allow-list on its CN, and forward the verified identity to the app in `X-Client-CN` |
| **Orders (FastAPI)** | Checkout. Rejects requests containing card numbers, then charges via payments |
| **Payments (FastAPI)** | Charges through the PSP; receives and verifies PSP webhooks |
| **Mock PSP (FastAPI)** | Stands in for a payment provider: requires mTLS with *its own* CA plus an API key |

### Trust domains

| CA | Issues | Trusted by |
|---|---|---|
| Internal CA | `edge`, `orders`, `payments`, `catalog` | edge and service sidecars |
| PSP CA | `psp-gateway` (server), `merchant-payments` (our client cert) | the PSP gateway, and payments when calling it |
| — | `attacker` (self-signed, claims `CN=orders`) | nobody |

An internal certificate is useless at the PSP, and a PSP-issued certificate is useless internally.

## Security controls and what the tests prove

| # | Control | Test | Expected |
|---|---|---|---|
| ① | Public TLS at the edge | Tokenized checkout through the edge | 200, `succeeded` |
| | | Declined card | 402 |
| ① | No raw card data (PCI scope reduction) | Checkout body containing a card number | 400 |
| | | Client that doesn't trust the edge's certificate | connection fails |
| ② ③ | mTLS between services | Orders sidecar with no client cert | rejected |
| | | Payments with a self-signed cert claiming `CN=orders` | rejected |
| | | Orders with a cert from the wrong CA | rejected |
| ③ | Authorization on identity | `edge` → orders | 200 |
| | | `catalog` → payments `/charge` | 403 |
| | | `edge` → payments `/charge` (may only deliver webhooks) | 403 |
| | | `catalog` → orders | 403 |
| ④ | Separate trust domain + API key for the PSP | Our internal cert → PSP | rejected |
| | | Merchant cert, no API key | 401 |
| | | Merchant cert + API key | 200 |
| ⑤ | Signed webhooks | Valid HMAC signature | 200 |
| | | Same event replayed | 409 |
| | | Tampered body | 401 |
| | | Valid signature, 10 minutes old | 401 |
| | | Unsigned | 401 |

"Rejected" means the request never reaches the application: either the TLS handshake fails or nginx answers `400 … SSL certificate` before any routing.

## Run it (Ubuntu / WSL)

```bash
sudo apt install -y nginx
cd ecommerce-lab
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt

./scripts/run_tests.sh      # start lab, run all checks, stop lab
```

To explore by hand:

```bash
./scripts/start_lab.sh
curl --cacert certs/internal-ca.crt -H "Content-Type: application/json" \
  -d '{"item":"sneakers","amount_cents":8999,"payment_token":"tok_visa"}' \
  https://localhost:8443/api/checkout
./scripts/stop_lab.sh
```

Certificates are created in `certs/` and secrets (PSP API key, webhook secret) in `run/secrets.env` on first start. Both folders are git-ignored. Delete `certs/` to issue fresh certificates.

The lab runs its own nginx on ports 8443 and 9101–9103 and doesn't touch the system nginx on port 80.

## Lab shortcuts vs. production

| In the lab | In production |
|---|---|
| Internal CA generated by a script | Managed private CA (AWS Private CA, GCP CAS, Vault PKI) or the service mesh's CA, with short-lived auto-rotated certs |
| One nginx process plays edge and all sidecars | Edge load balancer / ingress, plus a service mesh (Istio, Linkerd) or per-service proxies |
| Apps trust `X-Client-CN` because they listen on 127.0.0.1 | Kubernetes NetworkPolicy or security groups so only the sidecar can reach the app |
| Edge certificate from the internal CA | Public CA certificate (for example Let's Encrypt or ACM) |
| Secrets in `run/secrets.env` | Secrets manager or KMS, with rotation |
| Webhook replay protection in memory | Event IDs stored in a database |
| Mock PSP with mTLS | Most PSPs use TLS + API keys; some card-network and banking APIs require mTLS |
| Client sends `tok_...` tokens | Browser tokenizes the card with the PSP's hosted fields (e.g. Stripe Elements, Adyen Drop-in), so card data never touches our servers |
